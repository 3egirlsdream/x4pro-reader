# 游戏实现与搜索约束

`src/apps/AppRegistry.cpp` 注册 `game-2048`、`game-gomoku` 与 `game-mines`，复用已有原生应用工厂和应用菜单。
`Game2048.*` / `Gomoku.*` / `Minesweeper.*` 不依赖 Arduino、显示或存储，可以独立在主机验证；`GameSave.*` 适配 JSON/AppStorage，`GameActivity.*` 负责生命周期、输入和显示。

## 2048

棋盘使用 16 个字节存放二进制指数，按移动方向逐行压缩并只消费相邻相等项一次。改变后才生成随机数字；无效移动保持随机流不变。
xorshift32 状态随局面保存，可用固定种子重现；无浮点运算或动画。分数和极大数字采用明确的饱和边界。

## 五子棋 AI

1. 复制一份 225 字节棋盘作为搜索工作区，确保取消不会改变实际棋局；初始化一个合法备用落点。
2. 对所有空点检查四方向即时取胜与对手即时取胜。胜点优先于防守点；对手已有两个独立必胜点时可能无法全部防住。
3. 在已有棋子两格邻域内候选剪枝，以双方局部线型评分保留最多 12 点。邻域缓存为 29 字节位图。
4. 逐个暂放根候选，再扫描对手应点；仅评估原邻域或新增根棋子两格邻域。取最强应手作为惩罚，结合根棋子的攻击分选择落点。这是两层受限局部评估，并非全盘深度搜索。
5. 评分只读该点四条线内的五格窗口，识别直线及断开的三/四；不为每个节点重算整盘。每个根候选结束后撤销工作区棋子。

模型 `step(n)` 最多执行 n 个格点工作单元，不递归，不创建线程。一个单元的行扫描、局部窗口与邻域扫描都有固定边界。
标准最大工作量为 `225 + 12 × 225 = 2925` 单元，另有 4096 单元硬保护。
Activity 每次循环最多推进 32 单元，且每单元后检查 2,000 µs 切片目标；累计计算预算 200,000 µs，从首个推进切片起的墙钟预算 3,000 ms。
时间检查发生在单元/切片边界，因此 2 ms 与 200 ms 是协作预算，实际可超出一个有界单元/切片的时间；系统调度、绘制或外部面板暂停也会影响墙钟。
预算用尽立即结束搜索并采用已找到的合法候选；若战术扫描尚未完成，未扫描到的威胁不能保证已识别。
预算、主机测量与 MCU 真实性能分别记录，未从 Mac 数据外推 ESP32-S3 延迟。

搜索活跃时通过已有 `skipLoopDelay()` 机制请求 CPU 正常工作频率并让出调度，结束后恢复框架空闲节能逻辑。输入先于搜索处理，退出/菜单直接取消；休眠经 Activity 生命周期销毁游戏对象。

## 刷新和并发

输入修改、棋子/状态读取与渲染沿用 `RenderLock`，无第二个帧缓冲。思考过程中不逐节点请求绘制，只在开始/最终落子产生状态变化时请求。
棋子通过整数水平线段绘制，不逐像素重复测试整个圆盘。棋盘与文字随安全区域和主题布局，固定黑白保证子色可辨。
空闲循环没有绘制请求；强制刷新和系统关闭前光面板后的重绘会重建整个画面，避免错误的重复帧门控留下覆盖层。

## 扫雷

`MinesweeperActivity.*` 复用 GameActivity 的菜单、输入前置处理、方向、绘制锁和存档缓冲。共享布局/菜单改为虚函数提供格数和菜单项，原 2048、五子棋布局与输入测试保持通过。
固定最多 225 个状态字节，按位记录雷/翻开/旗，邻雷数最多读取八格即时计算；无需维护整盘计数缓存。
另一个 225 字节成员队列复用于首次生成和零区域连开。部分 Fisher–Yates 选雷每局最多 45 次，无随机碰撞重试；首格及其八邻格不进入候选池。
连开使用迭代队列，在入队之前标记已翻开，每格最多入队一次，无递归，无热路径堆分配；一次操作的最多 225 格工作在一次主循环内完成，只有结果变化才请求一次刷新。
数字格连开按旗数校验，错误旗可踩雷；胜利只取决于全部安全格翻开，不要求旗完全正确。
存档 schema 1，240 字节载荷校验难度/雷数/棋格位/终局/爆炸格/随机流，再经 AppStorage 备份轮换；验证临时对象采用一次 nothrow 堆分配，避免把模型及载荷同时放在小栈上。

## 扩展边界

没有在线服务、后台计时任务、深层 Minimax、置换表、MCTS 或连续动画；这些机制没有进入本次资源预算。
当前棋力目标为可离线对弈、即时胜点与单一直接威胁优先处理。复杂双威胁/长手杀棋不是已验证能力。
